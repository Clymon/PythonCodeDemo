LEARNING LAB — direct an AI coding agent with original Matt Skills

The instructor demonstrates, then each participant works independently.
Use student. The webpage is a working product to improve; its sample lessons are
product data. Your work is to make decisions, direct development and judge evidence.

1. ENVIRONMENT AND PRODUCT
   Clone student, prepare the recorded Python environment and run python app.py.
   Open a lesson, answer a question and refresh. Describe existing capabilities.
   Ask the agent to investigate relevant implementation facts when needed.

2. LLM, CONTEXT AND AGENT EXPLORATION
   Use the stepped token/context illustration, then docs/agent-exploration.txt.
   Ask what the project does; follow up on wrong-then-correct scoring behavior.
   Keep this exploration read-only. Observe actual Thinking/file/tool activity
   and explain how one retrieved result supports the answer. No planning Skill
   or greeting edit is required. Discuss sub-agents when they actually appear.

3. DISCUSS THE NEED — grill-me
   Begin with the open review request in docs/client-brief.txt. An acknowledgment
   such as I understand does not establish agreement on what the page should do.
   Compare two plausible policies after a wrong answer is later corrected: keep
   the past mistake, or remove the now-correct question. Decide the learning purpose.
   Then learn what a Skill is: reusable instructions for a task in SKILL.md, with
   optional supporting files. Read the original interview-method excerpt and use
   grill-me to discuss unresolved choices and confirm shared understanding.
   Check the actual Load skill record and the discussion that follows. The agent
   investigates facts and recommends options. Skill-to-Skill references and
   personal import are optional follow-up explanations after this first example.
   Choose rules and boundaries, ask about consequences and confirm shared understanding.
   Keep the discussion for the next stage. worksheets/decisions.txt is optional
   human note-taking, not a required output format imposed on the original Skill.

4. MAKE THE WORK READY — to-spec, then to-tickets when useful
   Use to-spec to synthesize the discussion. Confirm a useful public verification
   boundary; the agent explains what it catches and misses. Review scope/examples.
   Watch the to-tickets demonstration for complete, independently usable slices.
   Inspect and approve one actionable ticket within the short planning block.
   Judge what works after each ticket and which dependencies genuinely block it.
   The configured local tracker stores the spec and separate ticket files under
   .scratch/<feature>/ . Approve the breakdown before implementation.

5. IMPLEMENT ONE APPROVED TICKET — implement
   Select one ready ticket and use implement. It calls tdd where appropriate,
   builds one red/green behavior at a time, runs checks, calls code-review and commits.
   Agree on test boundaries before tests. Try the real page and inspect evidence.
   Explain Git diff/staging/commit with this first real feature change. If already
   committed, inspect git show HEAD. A commit is a delivery checkpoint; the human
   still accepts or requests revision.

6. CONTEXT AND CONTINUITY
   Distinguish durable project rules, on-demand Skills, shared vocabulary and
   current spec/tickets/evidence. Keep useful discussion together. A new task can
   implement a self-contained ticket using its saved references.
   Use handoff to simulate passing the project to another teacher. It writes a
   portable document in the OS temporary folder. Supply it to a fresh task in the
   project and check whether the recipient reconstructs decisions and next action.

7. REVIEW AND ACCEPT
   Read the Standards and Spec findings from code-review. Compare them with actual
   checks and browser behavior. A code review does not replace user acceptance.
   Check a normal case and a boundary; refresh/restart when saving is required.
   Use worksheets/acceptance.txt if helpful. State what remains unverified and
   decide accept/revise/continue with a reason.

Show a design choice, one complete ticket, a running result and an acceptance
reason. See docs/assessment.txt. Source tracing, hand-written Python, a test count
and a coverage threshold are not completion requirements. Instructor references
are on main and used only when requested or demonstrated by the instructor.
