LLM, CONTEXT AND THE AGENT LOOP

Generation
For the autoregressive text-generation model used in this lesson, each next
token is generated conditioned on the current sequence. Generated output is
appended for subsequent generation. A token is an input/output unit, not
necessarily a word. The demonstration's token boundaries are illustrative.

Context and working range
The current context is the information available to a model call. It can include
system rules, loaded project instructions, available tool definitions, user
messages/history, retrieved files/tool results and prior assistant output.
Smart zone/dumb zone describes a working-state risk as context becomes harder
to use; it is not two physical regions of a window or a fixed percentage/token
cutoff. Relevant facts are necessary; unrelated history, conflicts and irrelevant
detail can make the task harder. Model and task differences matter.

Harness and tools
WorkBuddy is the harness that selects context, connects the model to available
tools, manages task state and applies permissions. A model can request a tool
call; the harness executes permitted actions and feeds results back for later
model calls. One user question can involve several model calls and tool actions.
The visible activity list alone does not reveal an exact provider-request count.
Selecting a workspace does not automatically place its whole repository in context.
Tool definitions describe actions; tool results provide returned information.
AGENTS.md is project guidance and is distinct from the vendor's system prompt.

Reading the actual activity
Thinking: a visible processing status or summary, not a complete internal trace.
Read/Browse file: retrieving local project information, distinct from web browsing.
Tool use: executing an available action and returning its result. A grouped label
such as Run checks does not establish that tests ran; inspect the actual command.
Sub-agent: focused work can use a separate working context and return a report.
The details depend on the harness. A simple overview may need no sub-agent.
Explain delegation when it actually appears, such as the later two-axis review.

Skills and durable work
A Skill is a reusable set of instructions for a particular kind of task. Its
SKILL.md provides a name, a description of when to use it and method instructions.
The folder may also include supporting resources. The agent loads relevant
instructions into working context when needed. The first two exploration
questions require no planning Skill. First expose an unresolved product need and
two plausible meanings of it. The initial request may not settle the human
decisions, and an I understand reply alone does not confirm agreement. Then
introduce the concept and one method excerpt before demonstrating original
grill-me for discussing choices and confirming shared understanding.
Check actual loading and the resulting behavior. A loaded method still requires
human judgment. Agreement about desired behavior is different from the model
context containing instructions and facts; both matter. Explain importing Skills
or references between Skills only after
learners have experienced one method. Then synthesize and organize ready work. Specs,
tickets and handoffs preserve decisions and evidence across useful boundaries.
People decide goals, trade-offs, scope and acceptance; the agent investigates facts.

Context choices
Continue useful design discussion through spec/tickets. A self-contained approved
ticket can begin fresh with its references. Use handoff for real portability.
Compress at a useful boundary and inspect what survived. Starting fresh is a
choice, not a ritual after every message. Permissions are separate from model
selection and correctness. Use Code, the intended exercise folder and Default Permissions.
