FACILITATOR GUIDE — Learning Lab, English AI Agent Coding workshop

Purpose
Participants practise making design decisions, assigning complete tasks and
judging evidence while an agent investigates and implements a Python web product.
The Python/Git/testing lessons inside the webpage are sample product content.
The workshop route and timings are in docs/course-map.txt; the English delivery
script is distributed alongside the classroom deck.

Starting points
  student: the working starting product and blank collaboration records.
  main: an instructor reference, including a completed review feature.
  demo/agent-workflow: a recorded, incremental reference development sequence.
  docs/checkpoints.txt: current demonstration tags and historical tags.
Use student for class. Instructor examples express one chosen policy; participants
may make a different justified choice and should verify against their own spec.
The open request is docs/client-brief.txt. Source tracing is optional investigation.

Before class
Prepare accounts, model access, Git/Python and the recorded Python dependencies.
Clone student, create a local exercise branch and run python app.py in the prepared
environment. Use the browser at http://127.0.0.1:5050. Read README.txt for setup and
port alternatives. Configure Git identity locally on a shared training machine.
Import the five ZIPs only through the installed client's supported route. Keep
the safety scan and inspect the result. Current client observations and any
unverified steps are in docs/workbuddy-rehearsal.txt; import is not proof of use.

Delivery
Demonstrate briefly, then let each participant work independently. Start with the
tools, repository and operating the starting page. Delegate one greeting change,
check it and save it. Introduce Skills through the open feature discussion.
Use lab-discuss to record choices, lab-plan to agree on a spec and complete tasks,
lab-implement for one approved task and lab-review to map criteria to evidence.
Use lab-handoff when a fresh context is actually useful. These methods are selected
by need, rather than a compulsory sequence for every small request.

Reference design and slices
On main, the opt-in records are under instructor/worked-example/. The reference chooses
latest valid answer wrong; a later correct answer removes the question; original
quiz score stays unchanged; invalid input writes nothing; saved state persists.
T01 shows a readable current review list with links to the existing lesson.
T02 enables answering the listed question directly in review with saved correction.
Each slice has a user-visible outcome and its own evidence. The new demonstration
added one failing behavior check, implemented that behavior and checked it before
adding the next. The older review-red tag added a batch of checks and remains a
historical reference; it does not illustrate this incremental TDD sequence.
Raw build summaries and hashes: instructor/demo-build-evidence.json.
The incremental build was prepared with Codex, not executed by WorkBuddy.

Five-minute reference acceptance demonstration
1. Open the first lesson. For the input question choose B and Check answer.
2. Mark lesson complete. Observe reading progress independently of original score.
3. Open Mistake review. In T01, inspect the listed question and follow its link.
   In T02/final, correct the question directly in review by choosing A.
4. Inspect feedback, the remaining-review count and preserved original score.
5. Open the updated list and observe its empty state. Refresh/restart when the
   agreed persistence requirement calls for it. Ask what the evidence proves.
The wrong answer is controlled sample input, not an attempted AI-failure show.

Keeping exercises separate
Use separate copies for reference demonstrations and participant work. Save work
before changing branches. Git ignores instance/: switching commits does not clear
the local database. Browser cookies identify an anonymous practice profile.
Different ports alone do not isolate cookies; use separate browser profiles or
serial, isolated trials. Do not use reset --hard as a classroom navigation shortcut.

Acceptance and pace
Use docs/assessment.txt: decisions, complete tasks, evidence and continuity.
A participant may complete one useful verified slice and identify the next task;
the instructor reference is not a mandatory feature checklist. Ask the agent for
consequential technical explanations as needed. Neither source navigation, number
of tests nor a coverage threshold determines workshop completion.

Verification boundaries
Read docs/validation.txt for tests and browser observations. Windows lab setup,
network restrictions and installed-client invocation require target-device checks.
Keep any unverified behavior explicitly marked instead of presenting it as tested.
